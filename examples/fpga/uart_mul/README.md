# cmtz-mul

Multiplication in F_17 over the UART. The datapath is not hand-written: `cmtz_mul.v` and its testbench `cmtz_mul_tb.v` are generated by the Verilog backend of the Cook-Mertz compiler from this program:

```
field(17, 293);
embed(0, 1);
embed(1, 5);
mul(embed_0, embed_1) as m;
measure(m, mod_p) as product;
```

`mul` is the one primitive whose operands are both runtime values, so the two embeds become input ports (`in_embed_0`, `in_embed_1`, 5 bits each) and `product` becomes the output. The datapath is one pipeline stage: multiply, then reduce mod 17 with a chain of conditional subtracts (no `%`, which yosys would turn into a divider).

![Datapath of cmtz-mul: two UART request bytes into the two embed ports, the mul node and its reduction in one pipeline stage, one reply byte back out](diagram.svg)

## What it does

Send two bytes `a`, `b`, each 0 to 16, at 115200 8N1. The board replies with one byte, `a*b mod 17`. If `a` or `b` is 17 or more, the reply is `0xFF`. Wait for the reply before sending the next pair.

LEDs (active low): `leds[4:0]` show the last reply, `leds[5]` lights after an error reply.

Example: `03 05` replies `0F` (15), `10 10` replies `01` (16 * 16 = 256 = 15 * 17 + 1), `11 01` replies `FF`.

## Files

| File | What |
|---|---|
| `cmtz_mul_uart.v` | Top module `cmtz_mul_uart`: UART receiver, UART transmitter, and a small control state machine around the datapath. Hand-written. |
| `cmtz_mul.v` | The datapath. Generated. |
| `cmtz_mul_tb.v` | Datapath testbench: all 289 input pairs, expected values from the compiler's Python reference. Generated. |
| `cmtz_mul_uart_tb.v` | Whole-design testbench: sends every pair through a bit-banged UART and checks each reply against `(a*b) % 17`. |
| `pins.cst` | `clk` pin 4, `tx` pin 69, `rx` pin 70, LEDs pins 15 to 20 |
| `apio.ini` | Board and top module |

## Test

```
source ../../../env.sh
apio test        # prints PASS for both testbenches
```

## On the board

Loaded to SRAM on a Tang Nano 20K (`openFPGALoader -c ft2232 _build/default/hardware.fs`) and exercised over the on-board UART bridge with `uart_test.py`:

```
python3 -I uart_test.py        # a few pairs
python3 -I uart_test.py all    # all 289 valid pairs plus error cases
```

Result: all 289 valid pairs and the error cases (17 or more, 255) matched `(a*b) % 17`, with no mismatches. Pin 70 (`rx`) works with `PULL_MODE=UP` at 115200, and so does `tx` on pin 69. Not flashed.

Things to know:

- There is no resynchronization. The design pairs bytes strictly in order, so one dropped or extra byte shifts every later pair. In one run, sending several pairs without waiting for replies left the design half-way through a pair and the next pair's reply was `FF`. A clean run afterwards was fine. Wait for each reply, and power-cycle the board or send one extra byte if it gets out of step.
- The on-board debugger buffers UART output. Drain the port before a test, as `uart_test.py` does, or old bytes from a previous design will look like replies.
- Simulation: both testbenches print PASS under `apio test`.
